## Overall Impression

Pivot's decorative layer is disciplined and consistent — it looks like nothing else, in a good way. But three of the app's most emotionally-loaded screens (History, Insights, the streak banner) don't actually implement the product's own stated anxiety-reducing principles, and several basic interaction safeguards (submit-guard, delete confirmation, accessible nav labels) are missing. The single biggest opportunity: make "explain, don't punish fluctuation" a rule the code enforces everywhere numbers render, not a pattern that exists in exactly one banner.

## What's Working

1. **AuthView** (`src/App.tsx:251-301`) — live-verified at 1280px and 390px: one CTA, calm copy, correct Google branding, no clutter. The screen that most embodies "Quiet Clinician," and it holds up under real inspection.
2. **Spike-detection copy** (`InsightsView`, lines 932-942) — a concrete, working instance of "explain fluctuation, don't punish it": attributes a reading to "normal water weight fluctuation" instead of treating it as a verdict. ## Priority Issues

**[P0] Privacy Mode is silently ignored on the History screen.**
*Why it matters*: PRODUCT.md calls "hide raw numbers" "a respected, first-class way to use the app, not an edge case." Live-confirmed: with Privacy Mode ON, `HistoryView` (called at `App.tsx:208` with no `hideRawNumbers` prop passed at all) still shows every raw weight and every delta in full color. A user who explicitly opted out of seeing numbers sees them the moment they open the second tab.
*Fix*: Thread `state.settings.hideRawNumbers` into `HistoryView` and mask weight/delta the same way `Dashboard`'s `displayWeight()` already does.
*Suggested command*: `/impeccable harden`

**[P0] The velocity stat renders in alarm-red on zero data and on legitimate progress.**
*Why it matters*: Live-reproduced twice: a brand-new account with zero entries shows `0.00 lbs/week` in bold red (`InsightsView:949` — anything ≥0 gets `text-red-500`); a real, goal-consistent trend that hadn't yet turned negative also rendered red. Red is DESIGN.md's own "destructive actions and hard errors only" color, and this is a new user's very first screen.
*Fix*: Make the color goal-aware (the same `isLosing` pattern the Dashboard milestones already use), and give "insufficient data" its own neutral state instead of falling into the "bad" branch.
*Suggested command*: `/impeccable harden`

**[P1] Destructive actions are inconsistent, and one is mislabeled.**
*Why it matters*: Deleting a single History entry fires immediately with zero confirmation or undo, while the far less consequential "Reset All Data" shows a native `confirm()` — and its own handler comment admits it doesn't actually delete entries despite the label and dialog copy promising it does.
*Fix*: Add lightweight, on-brand confirmation (or undo) to entry deletion; make Reset All Data actually reset entries, or relabel it to match what it does.
*Suggested command*: `/impeccable harden`

**[P1] No submit-guard on the primary action creates duplicate entries.**
*Why it matters*: Live-reproduced: double-tapping "Save Entry" — exactly what a distracted, one-handed mobile user does — silently wrote two identical entries with no loading state or dedup check.
*Fix*: Disable the button and show a brief loading state from click to `onSave` resolution.
*Suggested command*: `/impeccable harden`

**[P2] Bottom navigation has zero accessible names.**
*Why it matters*: Confirmed via the accessibility tree: all five nav controls read as bare, unlabeled `button` nodes. A screen-reader user gets no information about what any of them do.
*Fix*: Add `aria-label` to each nav button and `role="switch"`/`aria-checked` to the toggle switches throughout Settings.
*Suggested command*: `/impeccable audit`

## Minor Observations

- `PredictionCard` (`App.tsx:1065-1072`) is defined but never rendered anywhere — dead code; `InsightsView` hand-rolls the same layout inline instead.
- Two different taglines for the same product: "Precision Weight Management" (Onboarding) vs. "Precision weight tracking for focused progress" (AuthView) — pick one.
- The motivational quote in Insights is generic fitness-app boilerplate; a Pivot-specific line about trend-vs-noise would reinforce the actual mechanism instead of generic encouragement.
- The active-tab nav pill renders as a near-black square in dark mode (live-confirmed) rather than a soft pill — `--theme-brand-50` maps to `--color-brand-900` (`#030712`) in dark mode, far too dark for a subtle "selected" wash.
- Native browser chrome leaks through at two "signature, chrome-free" spots: the Log Weight numeral shows default number-input spinner arrows, and the date picker uses the OS default calendar icon.
- Two color classes used without a theme-aware light/dark pair, per DESIGN.md's own "Don't" list: `text-red-500` (`InsightsView:949`) and `text-amber-500`/`text-brand-500` (`HistoryView:616,650`) — none of the `-500` variants are covered by `index.css`'s utility remap (only `-600` and a few `-50/100/200/900` steps are).
- Two chart-line colors (`#8b5cf6`, `#3b82f6` in the ECharts projection config, `App.tsx:901,904`) are outside DESIGN.md's documented palette (Assessment B, true positive).
- Duplicate near-simultaneous GET requests observed for `/api/entries`, `/api/profile`, `/api/auth/me`, and `/api/vapid-public-key` during normal use — worth checking whether this is React dev-mode double-invoke or a real subscription leak.
